# Fetarute 首页内容大纲

> 状态：进行中的内容方向。用途：为首页文案、图片选择与后续页面拆分提供共同判断依据；本文件不替代真实服务器信息、规则或加入流程的正式发布。

## 已确认的方向

- Fetarute 成立于 **2017 年**。
- 首页首先是一篇介绍 Fetarute 的作品：让第一次到访的人理解这里是什么、为何以铁路为线索、它由怎样的社区建设而来。
- Fetarute 由三个子服务器组成；它们通过 **服连快线（Serverlink）**
  运营的联络线连成一个整体。这个事实是首页解释「铁路为何重要」的核心。
- 首页不承担玩法说明或服务器操作手册的职责；不写分区玩法细节、游戏命令、版本要求、客户端准备或服务器地址。
- 目前唯一有效、应在首页明确呈现的加入入口是
  **QQ 门户群**。Discord、X、在线申请及其他旧入口暂不作为加入方式宣传。
- 现有的「线路导视 → 到站确认 → 铁路实景」开场是首页叙事的起点；首屏抵达后应继续介绍这座世界，而不是转入建站技术说明。

## 首页的一句话定位

**Fetarute 是一个自 2017 年起持续建设、由服连快线连接三个子服务器、地点与人的 Minecraft 社区。**

这句话用于统一判断，不要求原样显示。文案应保持具体、克制，避免把仍待确认的运营状态、功能或加入条件包装成既成事实。

## 推荐阅读路径

```text
抵达 Fetarute
  → 看见铁路如何连接世界
  → 认识共同建设世界的人
  → 知道这段旅程仍在继续
  → 前往 QQ 门户群了解加入安排
```

## 连续行程视觉语法

首页不是在末尾附加一张「访问总结」，而是从抵达到离开都由同一趟 Serverlink 行程串联。读者以原生滚动向下阅读；列车和线路只负责说明章节之间的关系，不替代内容本身。

### 无界连续构图

这不是 FurryGoods-Portal 那种把每段内容置于明确容器、再由壳层组织浏览的有界界面。Fetarute 首页应像穿过一张持续延展的平面铁路导视图：没有把整趟旅程框进画布的边线，线路可以从视窗外驶入、穿过内容之间的留白，再向下一段视窗外延伸。

- 每个 section 是内容上的章节，不是视觉上的封闭盒子；不为路线、列车或「本次到访」制造包住整段的外框。世界正文后的单一操作卡可以承接地图等明确行动，但不能把整段内容改造成卡片墙或独立应用面板。
- Serverlink 应作为贯穿整页高度的一条连续路径。视窗只是在这条路径上移动的观察窗口：向下滚动即是沿线路继续前进，而不是翻到一页新的站点画面。
- 列车的进度绑定文档的累计滚动位置，并在进入、经过和离开视窗时保持同一方向与身份。它可以暂时驶出可见范围，却不在章节切换时重置、传送或另起一趟车。
- 章节交界处以足够大的留白、线路转折和场景尺度变化来换气；不要以整齐的容器边缘、封闭背景块或浮层把上下内容切断。
- 终点牌是唯一有意的「收束」：它表示这次阅读的抵达，不把此前的行程改造成封闭的产品流程。

### 有选择地采用 Material Design 3 的交互语法

Material Design
3 在这里是**交互质量的参考**，不是首页的视觉皮肤或组件库。Fetarute 仍以铁路导视、扁平几何和无界连续构图建立身份；M3 只帮助可操作元素给出清楚、一致且可访问的反馈。

- 所有真实可操作元素（导航、语言与外观控制、公告条目、QQ 门户群入口）都应有可辨识的 enabled、hover、focused、pressed 与 disabled 状态。状态变化只改变局部色层、描边或轻微透明度，不改变按钮位置、点击范围或页面布局。
- 将快速反馈、面板展开与关闭、站牌显隐等非滚动动画收束为少量可复用的 motion
  token；它们服务于「发生了什么」和「下一步在哪里」，不为装饰而播放。
- Serverlink 列车仍严格由滚动进度决定。M3 式的缓动或物理感只可用于点击后的即时反馈，不能让列车弹跳、追赶用户滚动、擅自补间到下一站或制造假的实时运行感。
- QQ 门户群入口可以拥有明确的按压与焦点反馈，但外形仍是旅程终点的站牌／导视，而不是脱离叙事的圆角 M3 主按钮或悬浮 FAB。
- 移动端以可触及的目标尺寸、清楚的焦点与按压反馈、随空间调整的信息密度为优先；不照搬 M3 的导航栏、导航轨或多 pane 应用骨架。
- `prefers-reduced-motion`
  下保留状态可见性和内容层级，以即时但不突兀的状态切换代替位移、缩放、逐帧线路绘制与物理感动效。

### 主线与支线

- **服连快线（Serverlink）是首页的主线。**
  它的列车装饰沿一条连续联络线，依次经过三个子服务器的介绍，使「三个服务器构成一个 Fetarute」成为能被看见的结构。
- 每个子服务器拥有自己的停靠章节：只介绍它在整体中的位置、气质、代表性场景和与其他部分的关系；不在首页写玩法细节、命令或加入操作。
- 其他章节可以使用各自的线路装饰作为局部标记或支线，但不能切断 Serverlink 主线，也不能被误读成另一条把三个子服务器连在一起的联络线。
- 线路色与名称承载真实语义。Serverlink 的正式中英文名、线路代码、品牌色和三处停靠的规范名称确认后，应集中写入
  `src/data/`；未确认前不从既有线路色中借用或臆造。

### 滚动中的关系

这组动效由三个概念组成：**scroll-driven animation** 控制进度，**line drawing**
让 SVG 轨道随阅读逐段显现，**continuity transition** 让同一列车在相邻章节之间保持身份与方向。

```text
到站实景
  ↓ Serverlink 主线开始
联络线：为什么三个子服务器是一体
  ↓ 停靠
子服务器 A 的介绍
  ↓ 支线/局部线路装饰后回到主线
子服务器 B 的介绍
  ↓ 支线/局部线路装饰后回到主线
子服务器 C 的介绍
  ↓ Serverlink 到达终点
共同建设与近况 → QQ 门户群
```

- 列车位置应随实际滚动进度平滑 `translate`，而不是自动循环行驶、跳到下一站或表现为实时运行状态。
- 每次经过一个子服务器章节，可用站名牌和构图留白形成可读的停靠感，但列车位移始终由用户滚动驱动；离开时才让下一段轨道出现。内容本身不需要跟随列车移动。
- 桌面端允许主线在章节之间横向或斜向转折；移动端应收束为页面边缘的纵向轨道，保证阅读方向与触控空间。
- 视觉上可让轨道从首屏到站画面「驶出」，最终抵达 QQ 门户群前的终点牌；这使 CTA 成为旅程的下一站，而非突兀按钮。

### 扁平列车与线路

首页的列车和轨道延续启动动画的**扁平导视 UI**，而不是转成写实铁路插画、等距地图或 3D 漫游。它应让读者感觉开屏里驶过的同一班 Serverlink 列车，继续在页面的线路图上前进。

- 列车使用简洁的二维几何：实体车身、由背景色挖出的车窗、清晰的 1px 结构边；不画车头透视、车轮细节、金属高光、体积阴影或烟雾。
- 主线使用有明确方向的单一色带／线路图路径；以水平、垂直和受控的 45° 或 90° 转折表达连接关系，不使用消失点、枕木透视或逼真轨道材质。
- 读者滚动时，列车沿 Serverlink 路径以二维 `translate`
  前进，已走过的线段保持可见；这是开屏「列车驶过色带」的可阅读、可停靠版本，不是自动播放的背景动画。
- 每个子服务器章节的停靠点使用平面站名牌和短色带。其他线路可以从该停靠点分出，作为该 section 的局部导视；它们应在离开章节时视觉上回接 Serverlink 主线。
- 章节内容维持开放的阅读网格，列车与线路作为不设外框的独立导视层穿行于内容之间；它们不能遮挡标题、正文、链接、焦点样式或触控目标。

建议把页面末尾的「本次到访」做成**终点牌**而非汇总卡：列车停靠、主线结束、QQ 门户群成为下一站。这样“Visit
Summary”的感觉来自整趟连续行程，而不是额外叠加一个 UI 模块。

### 不变的边界

- 保持原生滚动，不使用整屏强制翻页、滚动劫持或滚动速度限制。
- 不复制 Portal 的固定壳层、页面边框、分栏容器或卡片化 section 节奏；首页的边界来自内容与留白，不来自包围它们的 UI 框架。
- 线路和列车是叙事装置，不显示虚假的列车班次、实时位置、里程或服务状态。
- `prefers-reduced-motion`
  下仍完整展示各段内容与线路关系，但停止逐段绘制和列车位移；不能让减少动态的读者失去结构信息。
- 动画只使用可组合的 `transform` 与
  `opacity`；轨道绘制应有静态回退，避免加载或低性能设备使阅读中断。
- 禁止 3D 透视、视差、拟物材质、玻璃浮层、发光粒子或持续循环的列车运动；这些都会打断启动动画已经建立的平面导视感。

### 00 · 抵达 Fetarute

**读者需要知道：** 我来到哪里？

- 承接开屏的站牌与到站实景，以「欢迎来到 Fetarute」建立抵达感。
- 用简短文字说明 2017 年的起点，以及这里是一座仍被持续建设的 Minecraft 社区。
- 首屏保留完整、安静的铁路场景；不堆叠地址、版本、服务器状态或多个行动按钮。

### 01 · 一座被连接起来的世界

**读者需要知道：** 铁路在 Fetarute 中意味着什么？

- 讲铁路如何把地点、建筑、记忆与人连接在一起，而不把它写成单纯的装饰主题。
- 先清楚交代三个子服务器并非彼此孤立：服连快线（Serverlink）作为品牌线路运营它们之间的联络线，使整个 Fetarute 成为可抵达、可穿行的整体。
- 可以从车站、换乘、沿线城市的视觉材料出发，但不在首页罗列线路编号、站序或地图功能。
- 这一章应建立世界的空间感，而不是解释每个子服务器的具体游戏机制。

### 01A–01C · 三次停靠

**读者需要知道：** 三个子服务器分别为整体带来了什么？

- 以三个连续 section 分别介绍三个子服务器；每段先给出正式名称和一句位置说明，再用一张代表场景或一则建设片段说明它的存在感。
- Serverlink 列车在每一段完成一次可读的停靠，局部线路装饰可以扩展该段的独特视觉语言，离开后仍回到同一条联络主线。
- 介绍应回答「这里在 Fetarute 整体中的意义是什么」，而不是展开为玩法功能表或新手教程。

### 02 · 从共同建设而来

**读者需要知道：** 这座世界是谁留下的？

- 用城市天际线、站台、街区与公共空间讲述长期建设的痕迹。
- 重点放在玩家、建筑、技术与管理共同维护一个可被继续使用的世界。
- 可使用具体的历史照片或建设片段；每项材料应有可核实的时间、地点或作者来源后再发布。

### 03 · 继续向前

**读者需要知道：** 这不是一座封存的展示品。

- 以少量、带日期的公告或近况说明 Fetarute 与官网仍在整理、建设和更新。
- 公告保持为清晰的时间线或列表，不抢占前面叙事章节的视觉空间。
- 没有可验证进展时，不以空泛的「即将上线」填充首页。

### 04 · 加入旅程

**读者需要知道：** 我下一步该去哪里？

- 首页只提供一个明确行动：前往 QQ 门户群。
- 推荐表达：**「想进一步了解 Fetarute 与当前加入安排，请前往 QQ 门户群。」**
- 审核、版本、客户端、规则与其他具体步骤在确认后进入独立指南；在此之前不编造或引用失效入口。

## 不应放入首页的内容

以下内容并非不重要，而是应在正式、可维护的独立页面或出口菜单中出现：

- 创造、生存、大厅等分区的玩法说明与游戏命令。
- Minecraft 版本、模组或客户端要求、服务器地址、白名单与审核细节。
- 实时在线人数、服务器运行状态、脱离世界上下文的通用地图入口与下载内容。三服汇可以在每个世界正文后提供一次按需 BlueMap：桌面端允许在车窗内启动，小屏只在新标签页打开，且都不得自动载入。
- 线路全表、连续站序、站码与细致的铁路数据查询。
- Discord、X、在线申请等当前无效或未确认的加入入口。

## 后续写作前的资料清单

在开始各章节的正式文案前，分别确认：

1. 可公开使用的历史照片、地点名称、拍摄/建设时间与署名；图片页先使用准确场景名，后续统一由 credit 页面承接完整来源。
2. 能代表「铁路连接世界」的 3–5 个真实场景或建设故事。
3. QQ 门户群的长期有效链接、加入说明与群内承接流程。
4. 第一批需要发布的近况、公告或历史节点，以及它们的准确日期。

确认后的长期事实应进入 `src/data/`；面向读者的公告、规则与指南应进入 Astro Content
Collections。本大纲只记录内容判断，避免成为第二套事实来源。
